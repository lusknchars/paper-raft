# Paper Raft — design

Date: 2026-10-12 · Status: draft for owner review · Licence: Apache-2.0

## 1. Purpose

Paper Raft is an open-source, controlled environment where AI agents reproduce research papers. A paper goes in. Out come independent implementations of its methods, each measured with the same tools against the paper's reference results, checked by a separate reviewer, and browsable in a static dashboard where every number links back to its code, its run and its page in the paper.

It is domain-agnostic: any paper with an implementable method and a checkable result can become a *study*. v1 ships one study, Ghia, Ghia & Shin (1982), to prove the loop end to end.

**Who it is for:** researchers and builders who want to try new techniques from papers and see, with evidence, whether they reproduce.

**Principles**
- One paper, one reproduced experiment, rerunnable from a clean checkout, before adding more agents or papers.
- Nothing silent: every gap in the paper is flagged; every result carries a status; failures are published too.
- An implementation never sees or edits the yardstick it is measured with.
- Harness-agnostic: the contracts are plain files; any agent tool (or a human) can do any stage. Claude Code is the first adapter.
- No API key is needed to rerun and check results.

## 3. Repository layout

```
paper-raft/
  raft/                     core library + CLI (harness-agnostic)
    contracts/              JSON Schemas for every hand-off file
    cli.py                  raft extract | implement | run | review | compare
  roles/                    agent role prompts, plain markdown
    extractor.md  implementer.md  reviewer.md
  adapters/claude-code/     .claude agents + skills that wrap the roles
  papers/                   gitignored; local PDFs
  studies/ghia-1982/
    paper.yaml              citation, DOI, local PDF path
    extraction.json         methods, equations, settings; page refs; missing flags
    problem/                shared and read-only for implementers
      setup.py              geometry, Re, boundary conditions, grid sizes
      measure.py            centreline sampling, error norms vs reference
      reference.json        Ghia's tables (Re = 100, 1000) with page refs
    methods/<name>/
      solver.py             implementation
      method.json           which extraction items it implements
    runs/<run-id>/
      manifest.json         inputs, params, package versions, git sha, seed
      results.json          sampled centrelines, errors, status, reason
    reviews/<name>.json     verdict, discrepancies, reviewed commit
  site/                     generated dashboard (not hand-edited)
  docs/
```

## 4. Contracts (JSON, each with a schema in `raft/contracts/`)

- **extraction.json**: list of items `{id, kind: method|equation|parameter|boundary_condition|result, text, page, quote, missing: bool, assumption?}`. Every item needs `page`. Any item with `missing: true` must have an `assumption`.
- **method.json**: `{name, implements: [extraction item ids], author_agent, notes}`.
- **manifest.json**: `{run_id, study, method, params: {re, grid, ...}, inputs_hash, git_sha, python, packages: {name: version}, seed, started_at, duration_s}`.
- **results.json**: `{run_id, status: ok|failed, reason?, samples: {u_vertical: [[y,u]...], v_horizontal: [[x,v]...]}, errors: {u_max, u_rms, v_max, v_rms}, tolerance, pass: bool}`.
- **reviews/<name>.json**: `{method, reviewed_sha, reviewer_agent, verdict: verified|discrepancies|unverified, discrepancies: [{file, line, extraction_id, page, description, severity}]}`.

**Status rule:** a run counts as *verified* only when `pass` is true, a review exists with verdict `verified`, and `reviewed_sha` equals the last commit that touched `methods/<name>/` as of the run's `git_sha` (so unrelated commits elsewhere don't invalidate a review, but any change to the solver does). Otherwise it is *unverified*, or *failed* when `status` is failed. The dashboard and the CLI derive status the same way, from one function in `raft/`.

## 5. Agent flow

1. **Extract.** An extractor agent reads the PDF and writes `extraction.json`. Gaps the paper leaves (e.g. convergence tolerance, corner singularity treatment, initial condition) become `missing: true` items, each with the assumption used.
   *Check:* `raft extract --validate` checks the schema and fails on any item without a page.
2. **Implement.** One implementer agent per method, in parallel, each in its own git worktree, writing only inside `methods/<name>/`. v1 methods:
   - `streamfunction-vorticity` (the paper's own formulation; a plain iterative solver stands in for multigrid, and that substitution is recorded as a missing/assumption item)
   - `projection` (fractional-step, primitive variables)
   - `lattice-boltzmann` (D2Q9)

   *Check:* a guard test fails if a method file is outside its folder, writes to `problem/`, or references `reference.json`.
3. **Run.** `raft run <method> --re 100 --grid 129` (or `--all`) imports `problem/setup.py`, calls the method's `solve(setup) -> fields`, samples with `problem/measure.py`, and writes the manifest and results. Divergence, NaN or timeout → `status: failed` with reason, still written.
   *Check:* rerunning a manifest reproduces the results within a recorded tolerance (1e-8 relative for deterministic solvers).
4. **Review.** One reviewer per method, never the method's implementer, compares the code against the cited extraction items and writes the review. Each discrepancy cites a file:line and a page.
   *Check:* schema validation, plus the `reviewed_sha` rule in §4.
5. **Compare.** `raft compare` scores every run against `reference.json` and builds `site/`.

**Method interface:** `solve(setup: CavitySetup) -> Fields` where `Fields` holds u, v (and optionally psi, omega) on a uniform grid over the unit square. `measure.py` handles interpolation to Ghia's sample points, so methods with different grids or lattices are compared identically.

## 6. Success criteria for v1

- At least one method reproduces Ghia Re = 100 on a 129×129 grid with max absolute error ≤ 1e-2 on both centrelines (u and v are normalised by lid speed) and is reviewer-verified.
- All three methods have runs and reviews (any status), and the failures are visible.
- From a fresh clone, `uv sync && uv run raft run --all --re 100 && uv run raft compare` reproduces the published numbers and site.
- CI (GitHub Actions) passes: tests, schema validation, guard test, a golden small-grid run, a rerun of every committed Re = 100 manifest, then a Pages deploy of `site/`.

## 7. Dashboard (`site/`, static)

- **Study overview:** a card per study with counts of verified, unverified and failed methods, plus headline errors.
- **Comparison view:** centreline plots (u along the vertical line, v along the horizontal line) with Ghia's points as markers and one line per method; selectors for method, Re (100, 1000) and grid (33, 65, 129) that switch between precomputed runs; an error table with pass/fail and a status badge; a streamfunction view per method and its difference from a chosen baseline.
- **Provenance drawer:** shows the manifest, the review verdict and discrepancies, a GitHub link to the solver at the run's commit, and the paper pages behind it.
- **Extraction view:** equations and settings with page references; missing items marked clearly.
- Plain HTML/JS, one charting library pinned from a CDN, data read from the JSON files, no server. Dark monospaced style, plain and readable.

## 8. Testing

- Unit tests: `measure.py` interpolation and norms on hand-computed fields; status derivation; manifest hashing.
- Schema tests for every contract, with sample valid and invalid files.
- Guard test (yardstick isolation).
- Golden run: each method on a 33×33 grid at Re = 100 within a loose tolerance, fast enough for CI.
- Reproducibility test: rerun committed manifests and compare results.

## 9. Out of scope for v1

Added on 2026-10-12 at the owner's request, and so **in** scope: `raft new <id>` scaffolds a draft study, and `--all-studies` validates, runs and reproduces every non-draft study in one command; CI uses it.

Out of scope: the live agent feed / mission-control view; a guided "bring your own paper" walkthrough; Codex/Gemini/OpenCode adapters; GPU solvers; Re above 1000; hosted execution.

## 10. Open-source hygiene

README with the 3-command quickstart, a CONTRIBUTING guide on how to add a method and a study, CITATION.cff, attribution of Ghia et al. for the reference data, a code of conduct, and issue templates for "new study" and "reproduction failed".

## 11. First study from the collection: transduced language models (amended 2026-10-13)

The Ghia PDF did not arrive, so it is parked as a draft. At the owner's request, the first reproduced study comes from the papers already collected in the Paperraft briefs (`github.com/lusknchars/ai-radar`, live at `paperaft.vercel.app`). The chosen paper is Snæbjarnarson et al. (2026), *Stochastic Estimation of Transduced Language Models*, arXiv:2608.27428, CC BY-SA 4.0. Of the six candidates checked, it is the one that can be reproduced on a laptop CPU.

- **Experiment.** DNA → amino-acid prefix probabilities (§4.3–4.4, Appendix E). There are five methods, one per agent: `beam_summing`, `smc_simple`, `smc_rb`, `beam_swor` and `beam_swor_adaptive`.
- **Cases.**
  - `worst`: Appendix E, a uniform source with the target isoleucine × 100. The answer is known in closed form.
  - `bigram`: a stand-in DNA bigram and three length-10 targets, with exact answers from Appendix D path sums. This case is the headline result.
- **Grading is by claim, per method** (`measure` takes the method name):
  - `exact`, for the worst case
  - `top_m_share`, for beam search in the worst case
  - `unbiased`: within 4 standard errors over 64 seeds, and the error falls with M
  - `lower_bound`, for prune_τ
- **Display only.** Table 2's numbers come from the paper's own unnamed corpus and targets. They are shown for the ordering of methods and never graded.
- **Honesty rule.** The study page states plainly what is not covered: the WikiText-2/PTB text experiments, GPT-2, and the paper's exact Table 2 values.
- **Linking.** `paper.yaml` carries `brief_url`, and the results explorer links to the brief. The brief in ai-radar links back to the lab, through a pull request on that repo. Nothing is deployed to Vercel without the owner's consent.
